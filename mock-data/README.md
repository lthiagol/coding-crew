# mock-data

Mocked task data — tasks across every lifecycle stage, plus edge cases. Text is
lorem ipsum; the shape is what matters.

Generated by [`generate.py`](generate.py):

```sh
python3 mock-data/generate.py
```

The folder mirrors a managed project's data folder, so it can be copied into a
project as-is.

```
mock-data/
  coding-crew/
    work/TSK*.json
```

## The set

| phase | count | shape |
|---|---|---|
| `draft` | 5 | title only — three, one child of an approved task, one promoted bug |
| `groomed` | 3 | intent, scope, criteria; one carries a `blocked` overlay |
| `approved` | 4 | criteria covered by steps, every step has `done_when`; one carries a `blocked` overlay, one a claim held elsewhere |
| `executing` | 3 | claimed with a lease, evidence attached; one defers a criterion |
| `code-review` | 3 | steps settled, self round filed, one open finding |
| `remediating` | 3 | external round, `changes-needed`, findings open |
| `needs-human` | 3 | five external rounds exhausted |
| `done` | 5 | clean verdict, no open findings |

Every fixture satisfies the gates of the phase it is in.

## Dependencies

Dependencies may point forwards or backwards in id order. The graph has no
cycles and `depends_on` always points at a task that exists. The claim gate is
what makes a wait real: `start` requires every dependency `done`, so a task
past `approved` waits only on done work, and the `done` set is closed under
its own waits-on edges. An `approved` task may wait on unfinished work — that
is what holds it. Four shapes are covered:

- **forward edges** — the phase tasks past `approved` — `executing` through
  `needs-human` — wait on the `done` tasks `TSK22`–`TSK26`, whose ids are
  higher: the gate, not the id order, is what makes a dependency real
- **fan-in** — most tasks wait on two others; the last `done` task waits on
  three
- **chains** — the `done` tasks form a chain among themselves
- **waiting on a blocked task** — `TSK07` waits on `TSK05`, which
  carries a `blocked` overlay, so it cannot start until it is unblocked

## The reasons a task is not claimable

An `approved` task can be held by three things, and one fixture covers each.
The overlay case and the claim case wait only on done work, so each is held by
one reason alone:

| reason | fixture | what holds it |
|---|---|---|
| a dependency that is not done | `TSK07` | it waits on `TSK04` and `TSK05`, neither done |
| an overlay | `TSK08` | it carries a `blocked` overlay; its only dependency is done |
| a claim held elsewhere | `TSK09` | another session holds the claim; its only dependency is done and its lease expires on `2099-12-31T00:00:00Z`, so it is held whenever the fixtures are read |

## Use in tests

```rust
let store = Store::new(repo_root().join("mock-data/coding-crew/work"));
let task = store.load("TSK07")?;
```

`repo_root()` is `CARGO_MANIFEST_DIR/../..` from a crate under `crates/`.

`crates/core/tests/mock_data.rs` checks the set: it loads, covers every
phase, keeps the gates, and has a sound dependency graph.
