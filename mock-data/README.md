# mock-data

Mocked task data — tasks across every lifecycle stage, plus edge cases. The text
is this project's own work; the shape is what matters.

Generated by [`generate.py`](generate.py):

```sh
python3 mock-data/generate.py
```

The folder mirrors a managed project's data folder, so it can be copied into a
project as-is.

```
mock-data/
  coding-crew/
    activity.json
    runtime.json
    work/TSK*.json
```

## Dependencies

Dependencies may point forwards or backwards in id order. The graph has no
cycles and `depends_on` always points at a task that exists. The claim gate is
what makes a wait real: `start` requires every dependency `done`, so a task
past `approved` waits only on done work, and the `done` set is closed under
its own waits-on edges. An `approved` task may wait on unfinished work — that
is what holds it. Four shapes are covered:

- **forward edges** — the phase tasks past `approved` — `executing` through
  `needs-human` — wait on the `done` tasks `TSK22`–`TSK26`, whose ids are
  higher: the gate, not the id order, is what makes a dependency real
- **fan-in** — ten tasks wait on nothing, eleven on a single task, eight on a
  pair; the last `done` task waits on three
- **chains** — the `done` tasks form a chain among themselves
- **waiting on a blocked task** — `TSK07` waits on `TSK05`, which
  carries a `blocked` overlay, so it cannot start until it is unblocked

## The reasons a task is not claimable

An `approved` task can be held by three things, and one fixture covers each.
The overlay case and the claim case wait only on done work, so each is held by
one reason alone:

| reason | fixture | what holds it |
|---|---|---|
| a dependency that is not done | `TSK07` | it waits on `TSK04` and `TSK05`, neither done |
| an overlay | `TSK08` | it carries a `blocked` overlay; its only dependency is done |
| a claim held elsewhere | `TSK09` | another session holds the claim; its only dependency is done and its lease expires on `2099-12-31T00:00:00Z`, so it is held whenever the fixtures are read |

## Use in tests

```rust
let store = Store::new(repo_root().join("mock-data/coding-crew/work"));

```

`repo_root()` is `CARGO_MANIFEST_DIR/../..` from a crate under `crates/`.

`crates/core/tests/mock_data.rs` checks the set: it loads, covers every
phase, keeps the gates, and has a sound dependency graph.

## The journal

`coding-crew/activity.json` is the project's activity journal, beside `work/`
and not inside it. Its events follow the fixtures' own histories: a task's
`created` comes first, its events keep the order its status history has them,
and a claim comes after the completion of the work it waits on. The set is
longer than the Overview's activity block shows, so the left-out count is
real. The kinds are provisional; nothing writes the journal yet.

## The runtime record

`coding-crew/runtime.json` is the flow's runtime record, beside the journal.
It is provisional: nothing writes it yet, and the shape is in
[task-model.md § 11.2](../docs/tasks/task-model.md#112-the-runtime-record-provisional).

The record tells a run, and the generator states it: `RUN_QUEUE` and
`IN_FLIGHT` in `generate.py`. The run's queue, in order:

| what | how |
|---|---|
| the queue | `TSK22` and `TSK25` done, `TSK14` in flight, `TSK29` and `TSK07` approved and waiting |
| the crew | one per role: the orchestrator idle; the builder and the reviewer both hold `TSK14`, the builder idle and the reviewer reviewing |
| the run | `started_at` is before the first claim the run holds |
| the round | `TSK14`, its second external round, after a first round that raised findings |
| the budget | 2 rounds used of the task's limit of 5 |
| the findings | 1 open: the task's own open high finding; the first round's other findings are fixed |
| the stamp | the flow runs |

The fixtures are checked against the run: each queued task's status is the
fixture's own, the waiting ones are approved with no overlay, the held task is
in `code-review`, and the findings and the limit are the held task's own. The
task's own review holds its external round, whose high finding is still open
and whose medium findings are fixed, after the self round, which found
nothing. The record's `raised` count is checked against that round.

The held task reaches its second external round through a `re_review` the
fixture cannot stamp: the model has no re-review record yet (talita's design
adds that record). So the open high and the fix times are the runtime's story, not the
fixture's.
